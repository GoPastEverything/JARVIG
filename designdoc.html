AAA Engine Platform
Project Start & Technical Framework

A portable, implementation-oriented engineering bible for building a new editor-first engine from a PlayCanvas-derived runtime, designed for real-time authoring, FPS/vehicle gameplay, seamless large worlds, multiplayer, UE-class PBR/material authoring, and a measured virtualized-geometry research program.

Status: Architecture DraftVersion: 0.2Date: 2026-09-22Primary rule: Editor contains the real engine

1. Project Charter

Build one engine platform with several hosts—Hub, Editor, Game Client, Dedicated Server and CLI tools—where the editor is a first-class host of the exact runtime systems used by the shipped game.

Authoring

Live engine, not a mock viewport

The editor viewport renders the actual runtime world. Play-In-Editor creates a controlled simulation world with rollback.

Scale

Large world from day one

Hierarchical reference frames, partitioning, streaming and relevance are foundational contracts.

Rendering

GPU-driven baseline

WebGPU-first architecture, indirect work submission, visibility-driven resource residency and later representation virtualization.

Studio

CLI-parity and documented decisions

Critical editor operations have a CLI/API path; architecture changes require ADRs/RFCs so humans and AI agents do not drift.

1.1 Success criteria

  • Create/open a project in the Hub and author it entirely in the Editor.
  • Play, pause, step, eject, possess and stop PIE while preserving the authoring world.
  • Build client and headless dedicated server from the same project.
  • Traverse a world larger than resident memory without blocking content IO.
  • Walk inside a moving ship/vehicle while physics remains stable and FPS-precise.
  • Network that scenario with server authority and relevance-based replication.
  • Reproduce all derived content through deterministic command-line tools.
  • Benchmark experimental rendering systems against fixed baselines before promotion.

1.2 Explicit non-goals for the first phase

No marketplace, no finished cinematic suite, no full server mesh, no attempt to duplicate every Unreal feature, and no claim that experimental microgeometry is superior to Nanite before objective testing.

  • Every editor mutation is a command/transaction.
  • Panels never mutate arbitrary runtime objects directly.

  • Runtime state carries origin tags so accidental save-back is impossible.

12A. Materials, PBR & Surface Authoring

Materials are a first-class authored asset system, not a collection of hard-coded shaders. The goal is UE-class flexibility: artists can build reusable master materials, derive lightweight instances, import complete PBR libraries, layer surfaces, drive parameters at runtime and inspect the exact shader/texture cost before shipping.

Canonical shading baseline: physically based metallic/roughness rendering with linear-light math, explicit color-space metadata, image-based lighting, physically meaningful normals and consistent tangent-space rules. Advanced shading models extend this baseline rather than creating unrelated pipelines.

12A.1 Authoring hierarchy

Material Functionsreusable graph logic
→
Master Materialgraph + exposed parameters
→
Material Instancecheap parameter overrides
→
Runtime Instancegameplay-driven values
  • Material Graph: node-based graph with typed pins, comments, subgraphs, preview nodes and compile diagnostics.
  • Material Functions: reusable versioned graph assets; edits propagate to dependents through explicit dependency invalidation.
  • Master Materials: define supported features and exposed parameters for a family such as painted metal, terrain, skin or glass.
  • Material Instances: parent/child inheritance with scalar, vector, texture, enum and limited static feature overrides without rebuilding the entire authoring graph.
  • Runtime Material Instances: transient or persistent parameter blocks for damage, wetness, team colors, burn state, holograms and animation.
  • Material Parameter Collections: world/global parameter sets for time, weather, wind, biome values, shared gameplay states and render features.

12A.2 PBR texture-set contract

SemanticRules
Base Color / AlbedosRGB authored color; no baked lighting/specular. Alpha meaning is explicit.
NormalLinear data; tangent convention recorded at import. Y/green-channel inversion is metadata/conversion, never guesswork at runtime.
RoughnessLinear 0–1. Gloss/smoothness imports are converted reproducibly to the canonical roughness convention.
MetallicLinear 0–1; dielectric/metal workflow is canonical baseline.
Ambient OcclusionLinear; optional and treated as local/micro occlusion, not replacement for real lighting.
EmissiveColor-space aware with HDR intensity multiplier; capable of physically bright values.
Height / DisplacementSigned/unsigned scale and units recorded. May feed parallax, tessellation where supported, terrain, or virtual microgeometry paths.
Opacity / TransmissionExplicit blend/shading mode. Masked, translucent and transmissive paths are distinct.
Clearcoat / Anisotropy / SSSOptional extended channels enabled only by compatible shading models.

12A.3 Packed maps and external libraries

The import layer must accept common artist-library conventions without making the runtime depend on any one vendor or DCC. A texture-set wizard maps discovered files/channels into canonical semantics and saves the mapping as import metadata.

PBR Texture Set Import
 source files
   ├─ *_BaseColor / *_Albedo
   ├─ *_Normal
   ├─ *_Roughness or *_Gloss
   ├─ *_Metallic
   ├─ *_AO
   ├─ *_Height / *_Displacement
   └─ packed map (ORM / RMA / MRA / custom)
        ↓ explicit channel-map recipe
 Canonical Surface Inputs
        ↓ target cook
 virtual texture pages / compressed GPU textures
  • Configurable packed-channel recipes; ORM is not assumed to mean every external library uses ORM.
  • UDIM/tiled texture sets treated as one logical texture asset with independently streamable tiles/pages.
  • High-resolution source textures stay out of runtime packages; cooks generate platform-appropriate mips/pages/compression.
  • Texture arrays, atlases and bindless/indexed texture indirection may be used internally without changing authoring semantics.
  • MaterialX import/export is a planned interoperability layer after the native graph/IR is stable; USD Shade can be evaluated later through an RFC.

12A.4 Surface models

TierModels
Baseline productionDefault lit metallic/roughness, unlit, masked, transparent/transmissive, decal.
Advanced productionClearcoat, anisotropic metal, subsurface/skin, thin surface, cloth/fabric, foliage/two-sided.
Specialized / researchHair, eye, water, volumetric surface, spectral/dispersion approximations and custom shading plugins.

Each shading model has a documented GBuffer/forward requirement, lighting contract, fallback behavior and platform support matrix. Unsupported models degrade deliberately rather than silently compiling a broken approximation.

12A.5 Layered materials and masks

  • Reusable Material Layer assets and separate Layer Blend assets.
  • Per-pixel blends driven by authored masks, vertex color, height blends, slope, curvature, object/world position or procedural fields.
  • World-aligned/triplanar projection for terrain, architecture and large props.
  • Detail normals, macro/micro variation and stochastic/aperiodic texture sampling hooks.
  • Decals and mesh decals integrate through the same surface attribute model.
  • Runtime Virtual Surface pages may cache expensive terrain/layer composition where measurement shows a benefit.

Cooked Material + Instance parameter layouts

The authored graph never directly stores backend shader source as its meaning. A stable intermediate representation lets the engine change renderer backends, optimize graphs and test compiler output without destroying artist assets.

Permutation rule: static switches are intentionally scarce. Every static option multiplies shader variants; the compiler records variant count, compile time, instruction/resource estimates and reasons. Dynamic branching or data-driven parameters are preferred when they are cheaper overall.

12A.10 Geometry integration

Materials and virtual geometry are designed together. A material can expose displacement/micro-surface descriptors to the virtual-geometry path without forcing every surface to generate geometry. The renderer chooses among normal/detail mapping, parallax, explicit displacement or transient procedural microgeometry based on feature support, screen-space error and budget.

12A.12 Validation & promotion gates

  • Golden PBR spheres match reference scenes within defined image tolerances.
  • Color-space and normal-orientation test fixtures catch import mistakes.
  • Material instances alter parameters without recompiling unrelated graph structure.
  • Graph/function dependency edits invalidate exactly the affected derived data.
  • Static permutation budget is enforced in CI.
  • Texture streaming remains bounded under high-resolution PBR-library stress scenes.
  • Material/texture asset loss or eviction always has a deterministic fallback.
  • Cook output contains no editor-only source imagery or graph metadata unless explicitly requested.

13. Virtual Geometry / “Beyond Nanite” R&D

Research discipline: First establish a defensible virtualized-triangle baseline. “Better than Nanite” is a hypothesis, not an architectural assumption.

13.1 Baseline

  • Offline meshlet/cluster decomposition.
  • Hierarchical geometric-error metric.
  • Compressed bounded pages.
  • GPU LOD/cluster selection.
  • Resident parent fallback when child pages are missing.
  • Streaming feedback for higher-detail pages.

13.2 Procedural microgeometry experiment

The optional procedural detail/aperiodic concept is considered as a detail distribution mechanism, not a universal mesh topology. Combine candidates such as blue-noise distributions, stochastic fields, Wang-like tiling, aperiodic rules, SDFs and deterministic seeds.

Surface Descriptor
 ├ macro material
 ├ stochastic / aperiodic rule set
 ├ displacement or SDF field
 ├ feature-density curves
 ├ scale domain
 └ deterministic seed
      ↓ GPU compute
 transient microdetail only where resolvable

13.4 Required metrics

  • GPU frame time at matched quality.
  • screen-space geometric error.
  • VRAM/resident memory.
  • storage size and streaming bandwidth.
  • page fault rate and latency sensitivity.
  • cook time.
  • temporal stability.
  • authoring complexity.
Production gate: experimental systems remain optional until they show a repeatable win and have a graceful fallback.

14. VFX / Particle System

VFX is a dedicated GPU simulation/graph system—not a substitute for geometry virtualization.

  • GPU emitter/simulation buffers.
  • sprite, ribbon, mesh, volume and decal renderers.
  • event chaining and collision interfaces.
  • deterministic seed modes for replay/tests.
  • budget classes for critical vs cosmetic effects.
  • graph compiler to GPU passes/kernels.

15. Terrain & Planetary Scale

  • Clipmap/quadtree or equivalent continuous terrain LOD.
  • Virtual texture/material pages separate from world entity cells.
  • Road/river/decal layers composited independently.
  • Procedural scatter stays data-driven until gameplay interaction requires entities.
Sequence: validate moving local frames + large terrestrial test world before attempting a full planet. Planetary scale must exercise existing contracts, not create a second world system.

21. Scripting & Plugins

Gameplay scripting begins with TypeScript/ES modules. Performance-sensitive or ecosystem-driven modules may later use WASM/native boundaries with explicit ABI contracts.

{
  "id": "com.example.vehicle-tools",
  "version": "0.1.0",
  "engine": "^0.4.0",
  "entryRuntime": "./dist/runtime.mjs",
  "entryEditor": "./dist/editor.mjs",
  "permissions": ["asset.read", "editor.panel.register"]
}

Never expose raw internal object pointers as the plugin ABI. Capabilities and permissions should be explicit so future collaboration/marketplace work is possible.

24. Security & Trust Boundaries

  • Downloaded project plugins are untrusted relative to the Hub/update system.
  • Collaboration never auto-executes arbitrary remote code.
  • Importers validate sizes/types and run in workers/sandboxed processes where practical.
  • Server never trusts client position, damage, inventory or entitlement claims.
  • Binary update signing is designed before public distribution.

29. First AAA-Style Vertical Slice

This demo is an architecture torture test, not a content showcase.

  1. Player spawns in a streamed outdoor range.
  2. Walks into a drivable spacecraft/large vehicle.
  3. Vehicle moves quickly while player walks inside.
  4. Player fires a weapon and moves physics objects inside.
  5. Vehicle crosses partition boundaries.
  6. Second client observes the same scenario through a dedicated server.
  7. Player exits to a different local/world frame.
  8. Editor can eject and inspect while PIE is active.
  • No obvious transform jitter at validated scale.
  • No blocking content IO during normal traversal.
  • Momentum is credible across frame transition.
  • Server build has no graphics/editor dependency.
  • Client cannot authoritatively self-teleport or self-award state.
  • Replay reproduces a scripted traversal.
  • Profiler exposes CPU/GPU/streaming/network costs.
